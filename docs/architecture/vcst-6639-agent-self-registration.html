VCST-6639 · Reference architecture · draft 1 · 2026-11-06

AI agents connect with the MCP URL only

Client ID Metadata Documents (CIMD), consent and least privilege on the platform's OpenIddict server, so that Claude, ChatGPT and IDE agents reach /admin/mcp and /ucp/mcp without an administrator registering each one.

vc-platform 3.1095 · OpenIddict 7.7.2vc-module-mcp (PR #1)vc-module-ucp (PR #13)vc-frontendAdmin Shell 3.1094 · classic Manager 3.1096

Summary

Today an agent can sign in only after an administrator registers it in Security → OAuth applications (VCST-6641). That works for a company's own agents. It does not scale to hosted clients: a merchant cannot pre-register claude.ai or ChatGPT for every store, and a buyer cannot ask a store to do it at all.

The MCP authorization specification (2026-07-28) makes Client ID Metadata Documents the way a client identifies itself to a server it has never met. Pre-registration stays as the fallback. Dynamic Client Registration (RFC 7591) is now deprecated. With CIMD the client_id is an https URL. The authorization server fetches the JSON document at that URL and takes the client's name and redirect URIs from it.

Claude Code, claude.ai, ChatGPT and VS Code already send CIMD. No commerce platform accepts it yet, and OpenIddict does not support it.

Recommendation. Implement CIMD in vc-platform as a client resolver in front of OpenIddict's client validation. On first use it turns a metadata document into an ordinary OpenIddict application: public, PKCE S256, explicit consent, code and refresh-token grants, and only the MCP resources the platform lists. Everything downstream works unchanged: tokens, stored authorizations, Connected agents, Disconnect, audit, and the MCP token rules.

The MCP module decides, per scope, whether self-registered clients may connect at all: Allowlist or Open. The UCP module needs no code. The storefront gains a branded consent page for buyers in phase 2. Dynamic registration is left out, since the specification has deprecated it.

High relevance

Back office · /admin/mcp

Marketers connect Claude Desktop, claude.ai or ChatGPT by pasting the URL. The administrator keeps control through consent, allowlists and Disconnect.

High relevance

Buyers · /ucp/mcp

Shopping assistants are hosted products that cannot be pre-registered per store. Without self-registration, link_buyer_identity works only for clients the merchant registered by hand.

Medium relevance

Storefront (vc-frontend)

Buyers already sign in through /oauth/authorize. The consent screen they then see is the platform's unbranded Razor page. It needs a storefront version, plus a place where buyers can revoke an assistant.

What VCST-6639 asks

  1. CIMD: accept an https URL as client_id at /connect/authorize and /connect/token. Validate the document: client_id equals the URL, plus redirect_uris, client_name and token_endpoint_auth_method: none. Treat the client as public with PKCE S256, match redirect URIs exactly, cache the document, and advertise client_id_metadata_document_supported.
  2. SSRF protection for the fetch: https only; no private, loopback or link-local addresses; limits on size, time and redirects; an optional host allowlist.
  3. Explicit consent naming the client, its host, the user and the MCP resource. The decision is stored and can be revoked.
  4. Least privilege: only authorization_code and refresh_token, the code response type and the requested rsrc:. The request to stop adding extra defaults in OAuthAppsController is already done by VCST-6641: POST /api/platform/oauthapps now stores exactly the fields sent.
  5. Dynamic client registration (RFC 7591) as an option, off by default.
  6. Tests and documentation.

Acceptance runs end to end. These must work:

  • claude mcp add --transport http virto https://<host>/admin/mcp without --client-id;
  • a claude.ai connector added with only the URL;
  • Deny returns access_denied;
  • private-address, mismatching or unlisted-redirect documents are refused;
  • tokens work only at their own MCP endpoint;
  • revoking the authorization stops the agent;
  • clients registered by an administrator keep working.

How other commerce platforms connect agents

Where the specifications are

  • MCP authorization 2026-07-28 (current) [1][3]:
    • Client ID Metadata Documents are SHOULD for both authorization servers and clients.
    • Dynamic client registration is MAY and marked deprecated: "new implementations should use Client ID Metadata Documents instead". In 2025-11-25 it was still plain MAY [4].
    • Clients try a pre-registered client first, then CIMD when the server advertises client_id_metadata_document_supported, then DCR.
  • Security considerations [5]: the server MUST clearly display the redirect URI hostname during authorization and SHOULD warn when every redirect URI is localhost.
  • IETF draft-ietf-oauth-client-id-metadata-document-03, 2 Nov 2026 [6][7]:
    • fetch: no redirects, no special-use IPs, about 5 KB maximum;
    • cache: a minimum and a maximum cache time, errors never cached, the last good document kept when a fetch fails;
    • redirect URIs: exact match, except loopback URIs match on any port;
    • client authentication: no shared secrets; reject a client_id equal to the server's own issuer;
    • consent: client_name and logo_uri are unverified.

No commerce platform documents CIMD today. Most require a pre-registered app (Shopify, Salesforce) or use DCR (Stripe, PayPal). Auth0, Okta, WorkOS, Stytch, Descope and Cloudflare already accept CIMD, and Keycloak has it as an experimental feature [45]–[55]. Okta makes the administrator allowlist each metadata URL first [47]. Virto would be the first commerce platform that lets any MCP client connect to the back office and to a store with nothing but the URL and the user's consent.

Agentic commerce protocols

  • UCP 2026-08-25 [41][42]:
    • The calling platform is identified by a profile URL: the UCP-Agent: profile="https://…" header, or meta["ucp-agent"] over MCP. The business fetches it under the same rules as CIMD (https, no redirects, no special-use IPs). Keys in the profile allow RFC 9421 signatures "without prior registration".
    • Identity linking is OAuth code with PKCE S256. The business MUST publish RFC 8414 metadata with authorization_response_iss_parameter_supported: true, scopes in {capability}:{scope} form, and revocation.
    • It does not say how the platform gets a client_id. CIMD fills that gap, and a CIMD document and a UCP profile are the same idea: an agent known by an https URL with published metadata.
  • ACP (OpenAI and Stripe, beta): an API key plus request signatures; no buyer account linking. Nothing maps to CIMD [43][44].

OpenIddict

  • No CIMD support. Issue #2552 is open; the maintainer will support it "once the specification is closer to adoption" [59]. Community PR #2416 was closed as too early. It built a virtual application (public, PKCE) when an https client_id was not in the store [60].
  • DCR is planned for 8.0 previews [61].
  • ChatGPT's private_key_jwt assertions are rejected by OpenIddict 7 by design (issue #2539). A custom handler can relax this [63].

So Virto writes the resolver itself, in the platform, behind OpenIddict's event model.

Relevance for UCP and the storefront

Today's buyer sign-in (VCST-5378)

A shopping assistant calls /ucp/mcp and gets 401. The protected-resource metadata names the store's origin as the authorization server. The assistant then opens /connect/authorize on the storefront host.

With Authorization:OAuthLoginPath set, the platform redirects to the storefront page /oauth/authorize (client-app/pages/auth/authorize.vue). The buyer signs in there as usual. The page exchanges the storefront session for a short platform cookie through POST /connect/session and returns to /connect/authorize.

Up to this point the flow is the same for any client. Only the last step, finding the client, fails for an assistant nobody registered.

What CIMD changes for buyers

  • Assistants connect to any store with no merchant setup. The store's /ucp/mcp resource is already listed by the MCP module's McpOAuthResourceProvider.
  • Consent becomes a buyer-facing screen. With implicit consent the buyer never saw which assistant they linked. A self-registered client must get explicit consent. Today that renders the platform's Views/Shared/Authorize.cshtml on the store's domain, with no store branding and only the application name and scope.
  • Buyers need to see and revoke linked assistants. Back-office users have Connected agents. Buyers have logout_buyer only from inside the assistant.
  • UCP's own agent identity is separate. UCP identifies the calling platform by its profile, and identity_linking is OAuth account linking. CIMD covers the OAuth half. The comparison above shows what the protocols say about the agent's identity.

Where the platform hooks in

OpenIddict validates client_id in its request-validation pipeline by calling IOpenIddictApplicationManager.FindByClientIdAsync. A scoped event handler, ordered just before OpenIddict's own client validation, runs on the authorization, token and revocation requests. When client_id is an https URL, it resolves the document and creates or refreshes the application. OpenIddict's own checks then run unchanged:

  • redirect URI match;
  • PKCE requirement;
  • grant, endpoint and rsrc: permissions;
  • the public-client rules.

The handler runs on every request with a URL client_id, but it fetches only when the cached document has expired.

serverBuilder.AddEventHandler<ValidateAuthorizationRequestContext>(builder => builder
    .UseScopedHandler<ResolveClientMetadataDocument<ValidateAuthorizationRequestContext>>()
    .SetOrder(/* before OpenIddict's ValidateClientId handler; verify the descriptor name in OpenIddict 7.7 */ 0)
    .SetType(OpenIddictServerHandlerType.Custom));
// the same for ValidateTokenRequestContext and ValidateRevocationRequestContext
serverBuilder.AddEventHandler<HandleConfigurationRequestContext>(builder => builder
    .UseSingletonHandler<AdvertiseClientMetadataDocumentSupport>());   // client_id_metadata_document_supported, "none" auth method

Platform design notes

Why materialize the client as an OpenIddict application

The alternative is a virtual client: a custom IOpenIddictApplicationStore that answers for URL client ids from the cache. It leaves no rows behind, but it breaks what VCST-6155 and VCST-6641 built on:

  • authorizations and tokens reference an application id;
  • Connected agents lists applications with rsrc: permissions;
  • Disconnect revokes by application;
  • the OAuth applications screen and audit show the application name.

A real row keeps all of these working. The cleanup job and the blocked flag keep the table bounded.

Consent rules

  • Self-registered clients always get explicit consent the first time, per user and per resource set. An administrator can raise a known client to implicit consent by registering it under its URL.
  • The stored authorization is permanent until revoked. It is invalidated when the document's redirect URIs change, or when a new resource is requested.
  • The screen shows the client host prominently (from the client_id URL, not from client_name), because the name is self-asserted.
  • Deny returns access_denied to the redirect URI, which Deny() already does.

Loopback redirect URIs are a requirement

Claude Code's document lists http://localhost/callback and http://127.0.0.1/callback with no port, and it listens on a random one. The CIMD draft and RFC 8252 §7.3 say loopback redirects match on any port. OpenIddict matches redirect URIs exactly.

So the resolver handler compares the request's redirect_uri to the document ignoring the port, and only for loopback hosts. If it matches, it adds that exact URI to the application before OpenIddict validates it. Without this, Claude Code cannot connect.

A client whose redirect URIs are all loopback gets a warning on the consent screen.

Revocation and UCP's metadata rules

The platform's metadata has no revocation_endpoint: tokens are revoked through the platform's own /revoke/token. UCP identity linking requires a revocation endpoint in the metadata, and self-registered agents need a standard way to sign out. The platform enables OpenIddict's /connect/revoke.

authorization_response_iss_parameter_supported is already true.

Security

ThreatControl
SSRF into the platform's network through the metadata URLhttps only. The ConnectCallback refuses private, loopback, link-local, CGNAT, multicast and IPv6 ULA addresses after DNS resolution, so DNS rebinding is covered. No redirects. 5 KB cap, 5 s timeout. An optional AllowedHosts, and a BlockedHosts list. Errors are not echoed to the caller.
Impersonating a known agentclient_id must equal the fetched URL exactly, and must not equal the platform's own issuer. The consent screen shows the client_id host and the redirect URI host, as the MCP spec requires. client_name and logo_uri are marked unverified; logos are served through the platform, or left out in phase 1. Only the host's own document can name its redirect URIs. A secret-based token_endpoint_auth_method is refused.
Code interceptionA public client with PKCE S256 required (plain refused for these clients, though the metadata still lists it), exact redirect URI match, and iss in the authorization response.
Over-broad tokensOnly the code and refresh-token grants. resource is required and must be an MCP resource from IOAuthResourceProvider. The audience is that resource only. No resource_server, no client_credentials, no password grant.
Consent phishingThe URL host, the logo and a "not verified by this store" note on the screen. The administrator can block a host or use allowlist mode.
Table growth from arbitrary URLsThe application row is created only after a valid document and an authenticated user. Request rate limit per IP. Cleanup job for unused clients.
A stale or changed documentCache with a minimum and maximum lifetime. Errors are never cached, and refetches are rate-limited. The last good document is kept when a fetch fails briefly. Refreshed on authorize and token requests after expiry. Re-consent when redirect URIs change.
A revoked agent keeps workingAlready covered: the MCP token rules check the token store on every request, and ValidateAgentTokensOnAllEndpoints covers REST and GraphQL.

Tests

  • Resolver unit tests:
    • valid document;
    • client_id mismatch;
    • missing redirect_uris;
    • token_endpoint_auth_method other than none;
    • non-JSON body, oversized body, timeout;
    • redirect response;
    • http URL;
    • a host that resolves to 10.x, 127.x, 169.254.x or ::1;
    • cache hit, expiry and Cache-Control.
  • Handler tests:
    • unknown URL client created; existing client refreshed; blocked client refused;
    • a resource outside the MCP list refused;
    • scope set to Off refused; client not on an Allowlist refused;
    • S256 required;
    • loopback redirect accepted on any port, non-loopback only exactly;
    • client_id equal to the issuer refused.
  • Controller tests: explicit consent forced for self-registered clients; re-consent after a redirect URI change; Deny returns access_denied.
  • E2E on the demo platform:
    • Claude Code without --client-id;
    • a claude.ai connector with the URL only;
    • ChatGPT, if it sends CIMD;
    • a fake metadata server for the negative cases;
    • Disconnect stops the agent;
    • the 27 UCP scenarios, with a self-registered client.

Decisions to make

  1. Defaults per scope. Proposal: CIMD on. Back office in Allowlist mode with Claude Code, claude.ai, ChatGPT and VS Code, like Okta's model. Buyers Open. Vendor portal Off. Explicit consent always.
  2. Client storage. Proposal: materialize OpenIddict applications, so that tokens, Connected agents, Disconnect and audit keep working. The alternative is virtual applications, the pattern of OpenIddict PR #2416, which leaves no rows but needs those features reworked.
  3. ClientId length. Proposal: widen OpenIddictApplications.ClientId from 100 to 400 characters with a migration on all three databases. The alternative is to refuse longer URLs. Today's known documents are 33 to 52 characters.
  4. Dynamic client registration. Proposal: do not build it. It is deprecated in MCP 2026-07-28, and Cursor and Gemini CLI can use a client registered in OAuth applications. The alternative is phase 3, behind a setting that is off by default.
  5. ChatGPT's private_key_jwt. Proposal: phase 1 with none only, and an E2E check that ChatGPT falls back to it. Add the client-assertion handler only if it does not.
  6. Buyer consent. Proposal: phase 1 on the platform page served on the storefront host, and the storefront page in phase 2. The alternative is both in phase 1.
